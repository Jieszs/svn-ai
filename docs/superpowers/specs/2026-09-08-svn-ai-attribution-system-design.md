# SVN AI代码归因与统计系统设计

## 1. 目标

建设一套适用于现有SVN研发环境的AI代码归因与集中统计系统，在不改变开发人员SVN提交习惯、不依赖公网、不上传提示词和完整源代码的前提下，实现：

- 记录Claude Code实际生成、修改的代码行；
- 将客户端归因记录与正式SVN版本号准确关联；
- 统计每次提交的AI代码增量、非AI归因增量和未归因增量；
- 持续维护当前版本中仍然保留的AI代码存量；
- 按人员、项目、部门、仓库和时间维度集中展示；
- 对采集缺失、关联失败和统计可信度进行显式标识。

目标规模为400名开发人员、160个SVN仓库。SVN服务端为VisualSVN Server Standard Edition 2.5.2，内置Apache Subversion 1.7.2；统计后台部署在Linux服务器，使用PostgreSQL。客户端同时支持Windows和Linux命令行环境，全部组件支持离线安装。

## 2. 范围与非目标

### 2.1 首版范围

- AI工具仅支持Claude Code；
- 支持Claude Code通过Edit、Write和Bash产生的文件变化；
- 支持TortoiseSVN、IDE SVN插件和svn命令行等任意正常提交方式；
- 支持文本源代码文件的逐行归因；
- 支持普通修改、删除、文件复制、分支复制、重命名和具备可靠mergeinfo的合并；
- 提供管理后台、统计API和CSV/Excel导出接口；
- 支持客户端、SVN Hook Agent和服务端的离线安装与升级。

### 2.2 非目标

- 不通过模型或代码风格推测AI来源；
- 不采集Claude提示词、回答正文或完整会话；
- 不对上线前的历史代码反向推断AI归因；
- 不在首版支持通义灵码、Cursor、Copilot等其他AI工具；
- 不评价代码业务质量，不将代码行数直接等同于业务ROI；
- 不改变SVN权限模型，不接管或包装开发人员的SVN提交命令；
- 不在SVN仓库中写入额外版本属性或归因文件。

## 3. 技术路线

系统沿用Git AI核心程序的技术路线，核心组件统一使用Rust开发：

- 客户端与常驻进程：Rust；
- VisualSVN Hook入队程序与异步代理：Rust；
- Linux统计服务：Rust、Axum、Tokio、SQLx；
- 数据库：PostgreSQL；
- 客户端本地缓存：SQLite；
- 管理页面：由Rust服务提供静态资源和JSON API，首版采用轻量页面与本地打包的图表资源；
- Windows安装：签名后的可执行文件及PowerShell安装脚本；
- Linux安装：静态链接可执行文件及Shell安装脚本；
- Linux服务端交付：离线压缩包和离线容器镜像各一套。

不引入Kafka、RabbitMQ等独立消息组件。服务端通过PostgreSQL任务表实现可靠异步处理，降低离线环境中的部署和运维复杂度。

## 4. 总体架构

系统由四个运行单元组成。

### 4.1 `svn-ai`客户端

安装在开发人员Windows或Linux电脑上，包含命令行程序和用户态常驻进程，负责：

- 安装、检查和卸载Claude Code Hook配置；
- 识别当前目录所属SVN工作副本、仓库UUID、仓库根地址、相对路径和基础版本；
- 在Claude Code工具执行前后建立文件状态快照并计算差异；
- 形成逐行AI归因事件并写入本地SQLite；
- 异步上报、失败重试、断点续传和版本自检；
- 展示客户端状态、待上传数量和最近一次成功上报时间。

### 4.2 `svn-ai-hook`

由VisualSVN仓库的`post-commit` Hook调用。该程序只执行以下操作：

1. 接收VisualSVN传入的仓库路径和版本号；
2. 将事件以原子方式写入VisualSVN服务器本地队列；
3. 在目标100毫秒内退出并返回成功。

该程序不执行Diff计算、网络请求或数据库操作，统计系统故障不得影响SVN提交。

### 4.3 `svn-ai-hook-agent`

作为VisualSVN服务器上的Windows服务运行，负责：

- 异步消费本地提交事件队列；
- 调用VisualSVN自带的`svnlook.exe`读取作者、提交时间、变更路径、copy-from、mergeinfo及版本内容；
- 在VisualSVN服务器本地计算文本行差异和代码行指纹；
- 向Linux统计服务上传不包含完整源代码的版本事件；
- 网络异常时保留事件并重试；
- 定时检查各仓库最新版本号，发现缺失版本后自动补采；
- 执行仓库首次接入时的历史基线扫描。

### 4.4 `svn-ai-server`

部署在Linux服务器，负责：

- 接收客户端AI归因事件和VisualSVN版本事件；
- 对事件进行认证、验签、去重和顺序控制；
- 将AI归因与SVN正式版本进行匹配；
- 按版本维护文件逐行来源和当前存量；
- 生成日、周、月及实时汇总指标；
- 提供管理页面、查询API、导出、权限和审计功能。

## 5. Claude Code归因采集

### 5.1 Hook事件

客户端安装以下Claude Code Hook：

- `SessionStart`：登记会话、工作目录和客户端状态；
- `PreToolUse`：在Edit、Write、Bash执行前开始一次归因事务；
- `PostToolUse`：工具执行成功后计算文件变化并提交归因事务；
- `PostToolUseFailure`：取消或关闭失败的归因事务；
- `SessionEnd`：结束会话并立即触发待上传事件刷新。

Hook通过标准输入接收Claude Code JSON事件，以`session_id`和`tool_use_id`关联同一次工具调用。Hook只调用本机`svn-ai hook`子命令，不修改Claude Code输出，不影响权限决策。

### 5.2 文件变化识别

- Edit和Write：根据工具输入识别目标路径，保存修改前快照，修改后只计算目标文件；
- Bash：常驻进程在工具执行期间记录工作副本内发生变化的文件，工具结束后只计算实际变更文件；
- 并行工具调用：每个`tool_use_id`维护独立事务，并在文件级串行合并归因；
- 工具失败：不产生AI新增记录，但保留必要的诊断状态；
- Claude Code未处于活动工具事务时发生的变化，不标记为AI生成。

### 5.3 行级归因事件

每条客户端事件至少包含：

- UUIDv7格式的事件ID；
- 客户端设备ID、客户端版本、SVN用户名；
- 仓库UUID、仓库根地址摘要、工作副本相对路径；
- 工作副本基础版本；
- Claude会话ID摘要、工具调用ID摘要、工具类型；
- 文件相对路径；
- 修改前后的行区间；
- 新增行的带密钥BLAKE3指纹和上下文指纹；
- AI新增行数、AI删除行数和事件时间；
- 可取得时记录模型标识，无法取得时明确存储为空值。

客户端不上传提示词、回答、会话全文和完整代码内容。

## 6. 代码指纹与隐私

### 6.1 指纹规则

- 以文件原始字节切分逻辑行；
- CRLF与LF统一视为行结束符，不进入行指纹；
- 行内空格、缩进和字符编码字节默认保留；
- 每行使用组织级密钥计算带密钥BLAKE3指纹；
- 同时计算包含前后相邻行的上下文指纹，用于处理重复代码行；
- 文件路径在传输前规范化为仓库相对路径，禁止出现本机绝对路径；
- 客户端与Hook Agent使用同一指纹版本和组织级密钥版本；
- 密钥轮换后，旧事件保留原密钥版本，后台可同时识别有效历史版本。

### 6.2 纯格式变化

系统为受支持语言计算辅助规范化指纹。仅当原始行指纹变化、辅助指纹一致且语言规则确认语义未改变时，沿用原来源并标记为格式变化。对于Python、YAML等缩进可能影响语义的语言，不忽略前导空白。无法可靠判断时按真实新增和删除处理，不进行猜测。

### 6.3 敏感数据控制

- 统计后台只保存代码行指纹、归因区间、路径和统计元数据；
- 统计页面和API不提供源代码浏览功能；
- 路径字段按角色授权展示，领导汇总默认不显示文件路径；
- 网络日志不得记录请求正文；
- 错误日志只记录事件ID、仓库ID、版本号和错误码；
- 管理员可吊销设备凭据和组织指纹密钥版本。

## 7. SVN版本采集与关联

### 7.1 版本事件

`svn-ai-hook-agent`针对每个SVN版本生成一个版本事件，至少包含：

- 仓库UUID、仓库标识和SVN版本号；
- 提交账号和提交时间；
- 变更路径及新增、修改、删除、复制类型；
- copy-from路径与版本；
- mergeinfo变化；
- 每个文本文件的差异操作：旧行起点、删除行数、新行起点、新增行指纹及上下文指纹；
- 文件类型、文件大小、是否被统计规则排除；
- 事件生成时间、Hook Agent版本和唯一事件ID。

版本事件不包含完整源代码。二进制文件只记录文件级变更，不进入代码行统计。

### 7.2 匹配条件

后台按以下条件由强到弱匹配SVN新增行与客户端AI归因：

1. 仓库UUID一致；
2. SVN提交账号与客户端绑定账号一致；
3. 仓库相对路径一致；
4. 客户端基础版本不晚于提交前版本；
5. 行指纹一致；
6. 上下文指纹、修改顺序和时间窗口一致；
7. 同一行只能被一个客户端归因事件消费。

强条件不满足时不得标记为AI。重复行导致匹配不唯一且无法通过上下文消歧时，标记为未归因。

### 7.3 到达顺序与最终一致

客户端事件和SVN版本事件允许任意顺序到达。后台对暂时无法匹配的数据执行延迟匹配：

- 新事件到达时主动唤醒相关仓库、账号和路径的待匹配任务；
- 待匹配事件保留30天；
- 正常统计目标是在SVN提交后5分钟内完成；
- 迟到事件匹配成功后自动重算相关版本、日报、月报和当前存量；
- 超过30天仍无法匹配的数据保留为未归因，并在数据质量页面展示。

### 7.4 部分提交

SVN提交只包含客户端AI修改的一部分文件时，后台仅消费本次版本中实际出现的匹配行。未提交文件对应的客户端归因继续保留，等待后续版本匹配。客户端更新或还原工作副本后，已经不存在的待归因内容由本地清理任务关闭，不计入AI入库行数。

### 7.5 AI生成行状态

每个AI生成行记录具有以下状态，避免尚未提交的代码被过早算作拒绝：

- `pending`：客户端已记录，但尚未进入SVN版本；
- `accepted`：已经与正式SVN版本中的新增行匹配；
- `discarded`：客户端确认该行在提交前被删除或替换；
- `expired`：超过30天仍未入库，且已经无法在有效工作副本状态中确认；
- `ambiguous`：SVN中存在相同行，但无法唯一确认对应关系。

实时页面单独展示`pending`数量。最终AI采纳率仅使用已经终结的`accepted`、`discarded`、`expired`和`ambiguous`状态，计算公式为`accepted ÷ (accepted + discarded + expired + ambiguous)`；最近30天数据同时标记为“可能继续变化”。

## 8. 当前代码存量维护

### 8.1 来源类型

后台为每个有效文本文件维护压缩的逐行来源向量，来源类型包括：

- `ai`：由Claude Code归因事件确认；
- `non_ai`：上线后新增但未匹配到Claude Code归因，且采集链路完整；该类型表示“非Claude Code归因或其他来源”，不作为绝对的人工创作证明；
- `unattributed`：采集链路不完整或存在匹配歧义；
- `legacy`：系统接入前已经存在的历史代码。

对外展示时不得把`unattributed`和`legacy`直接称为人工代码。

### 8.2 版本演进规则

- 未变化的代码行沿用原来源；
- 已确认AI新增行标记为`ai`；
- 在采集链路完整时，未匹配AI归因的新增行标记为`non_ai`；
- 采集链路不完整时，无法匹配的新增行标记为`unattributed`；
- 被删除的代码行从当前存量中移除；
- 人工重写AI代码时，旧AI行删除，新行按`non_ai`或`unattributed`处理；
- Claude Code重写其他来源代码时，新行标记为`ai`；
- 纯格式变化沿用原来源并记录格式变化标志；
- 文件和目录复制根据SVN copy-from信息复制来源向量，不计为新的AI生成或AI入库；
- 文件和目录删除移除对应当前存量；
- 具备可靠mergeinfo时，根据来源版本和行指纹继承合并来源；无法唯一确定时标记为`unattributed`。

### 8.3 历史基线

仓库接入时执行一次受控基线扫描：

- 以接入时指定的最新稳定版本作为基线版本；
- 统计有效文本文件和总行数；
- 所有基线代码行标记为`legacy`；
- 基线扫描完成前，该仓库不进入正式全库贡献率汇总；
- 基线完成后从下一版本开始按版本顺序增量维护；
- 系统不对基线以前的AI来源作推断。

## 9. 指标定义

### 9.1 提交增量指标

- AI生成行数：客户端观测到的Claude Code新增或重写行数；
- AI入库行数：进入正式SVN版本且匹配到AI归因的新增行数；
- 非AI归因入库行数：采集完整情况下未匹配AI归因的新增行数；
- 未归因入库行数：采集不完整或匹配存在歧义的新增行数；
- SVN新增总行数：AI、非AI归因和未归因新增行数之和；
- AI提交占比：AI入库行数除以SVN新增总行数；
- AI采纳率：状态为`accepted`的AI生成行数，除以状态已经终结的全部AI生成行数；`pending`不进入分母，最近30天结果标记为可能变化；
- AI删除行数：本期SVN版本中被删除的、此前来源为AI的代码行数；
- AI重写流失行数：本期被其他来源重写的AI代码行数。

### 9.2 当前存量指标

- 当前AI代码存量：目标版本仍然存在且来源为AI的有效代码行；
- 当前非AI归因存量：上线后仍然存在且来源为`non_ai`的有效代码行；
- 当前未归因存量：仍然存在且来源为`unattributed`的有效代码行；
- 历史存量：仍然存在且来源为`legacy`的有效代码行；
- 全库AI代码贡献率：当前AI代码存量除以当前全部有效代码行；
- 上线后AI代码贡献率：当前AI代码存量除以上线后新增且仍然保留的AI、非AI归因和未归因代码行总数；
- AI代码留存率：某一统计期AI入库代码中，在目标版本仍然保留的行数除以该期AI入库行数。

领导总览以“上线后AI代码贡献率”为主口径，同时展示“全库AI代码贡献率”和历史存量占比。

### 9.3 数据质量指标

- 客户端安装覆盖率；
- 客户端在线率和版本合规率；
- SVN Hook Agent健康率；
- SVN版本采集完整率；
- AI归因事件及时上报率；
- 未归因新增行占比；
- 待匹配事件数量和最长等待时间；
- 各仓库最新SVN版本与后台最新处理版本的差值。

## 10. 数据可信度

每个仓库、项目、部门和统计周期均计算可信度：

- `complete`：SVN版本连续、Hook Agent正常、相关开发人员客户端处于合规状态且不存在超时待匹配；
- `partial`：存在迟到事件、少量未归因或短暂客户端离线，但能够给出带缺口说明的统计；
- `invalid_for_assessment`：版本缺失、Hook Agent异常、客户端未安装或未归因比例超过配置阈值。

统计页面必须同时展示指标值和可信度。`invalid_for_assessment`数据不得进入考核汇总，但仍保留并展示异常原因。

## 11. 后台功能与权限

### 11.1 页面

- 领导总览：接入规模、AI生成、AI入库、采纳率、提交占比、当前存量、贡献率和趋势；
- 部门与项目分析：部门、项目、仓库、人员逐层下钻；
- 数据质量：客户端、Hook、版本连续性、待匹配和未归因情况；
- 系统管理：组织映射、仓库、统计规则、客户端版本、凭据和重算任务；
- 审计查询：查看指标对应的仓库、版本号和归因事件，不展示源代码。

### 11.2 角色

- 行级领导：查看全局汇总和部门趋势；
- 部门负责人：查看本部门和所属项目；
- 项目负责人：查看授权项目和仓库；
- 开发人员：查看本人及参与项目；
- 系统管理员：维护配置、凭据、版本和重算任务；
- 审计人员：只读查看统计来源、处理状态和操作日志。

组织、人员、项目和SVN仓库关系支持通过Excel批量导入，也支持后续对接内部组织系统。

### 11.3 指标使用分级

- 正式发布指标：接入人员、接入仓库、AI入库代码量、AI提交占比、当前AI代码存量、上线后AI代码贡献率、全库AI代码贡献率和数据覆盖率；
- 观察分析指标：AI采纳率、个人横向比较和部门排名；
- 所有指标均保留计算能力，页面明确标识使用级别；
- 默认不提供个人排行榜，防止以代码行数驱动错误行为。

## 12. 数据模型

PostgreSQL至少包含以下逻辑实体：

- `departments`：部门和层级关系；
- `users`：人员、SVN账号和部门归属；
- `devices`：客户端设备、凭据、版本和健康状态；
- `repositories`：仓库UUID、名称、基线版本和统计规则；
- `working_copies`：设备、用户、仓库和工作副本标识；
- `ai_sessions`：不含提示词的Claude会话摘要；
- `attribution_events`：客户端AI行级归因事件；
- `svn_revisions`：SVN版本、作者、时间和处理状态；
- `revision_file_changes`：版本内文件差异操作；
- `attribution_matches`：SVN新增行与AI事件的匹配关系；
- `file_provenance`：目标版本下压缩的文件逐行来源向量；
- `metric_snapshots`：按日及当前状态预聚合指标；
- `ingestion_jobs`：接入、匹配、重算和补采任务；
- `audit_logs`：登录、配置、导出、凭据和重算审计。

所有接收接口以事件ID或“仓库UUID＋版本号”作为幂等键。每个仓库的版本处理由数据库锁保证串行，不同仓库并行处理。

## 13. 安全设计

- 客户端、Hook Agent和后台之间仅通过内网HTTPS通信；
- 支持内部CA，禁止客户端关闭证书验证；
- 每台设备使用独立凭据，请求带时间戳、随机数和签名；
- Windows客户端凭据存入系统凭据管理区域，Linux凭据文件仅当前用户可读；
- VisualSVN Hook Agent使用独立服务凭据，不与开发人员凭据共用；
- 设备凭据支持吊销、轮换和最后使用时间审计；
- 后台实施基于角色和数据范围的访问控制；
- 导出、重算、规则修改和凭据操作全部写入审计日志；
- 安装包提供数字签名或SHA-256校验文件；
- 本地SQLite默认保留30天未上传事件，达到1GB时停止新增缓存并产生明确告警，不静默覆盖数据；
- 服务端原始事件默认保留365天，聚合指标和审计记录长期保留，具体期限可通过配置统一调整。

## 14. 可靠性与运维

### 14.1 客户端

- 先落本地SQLite再返回Hook调用；
- 上传失败采用指数退避并带随机抖动；
- 提供`svn-ai doctor`检查Hook、SVN工作副本、账号绑定、网络、证书和缓存；
- 提供`svn-ai status`显示版本、设备、仓库、待上传数量和最近错误；
- 客户端升级不修改或丢失本地事件数据库。

### 14.2 VisualSVN服务器

- `post-commit`只执行本地原子入队；
- Hook Agent以Windows服务运行并具备自动重启策略；
- 本地队列达到容量阈值时告警，但不阻塞SVN提交；
- 每晚使用`svnlook youngest`核对最新版本并补采缺失版本；
- 对160个仓库设置并发上限，避免批量扫描影响VisualSVN性能；
- 基线扫描和大版本处理可配置在非业务高峰执行。

### 14.3 服务端

- API接收与统计计算解耦，接收成功后写入持久任务表；
- 同一事件重复提交只返回已有结果；
- 同一仓库严格按SVN版本顺序推进；
- 失败任务指数退避，超过重试上限进入异常队列并告警；
- 支持按仓库和版本区间重放，重放结果保持幂等；
- 指标聚合可重建，不以聚合表作为唯一事实来源。

## 15. 性能目标

- VisualSVN `post-commit` Hook本地入队目标耗时不超过100毫秒；
- 正常网络和服务状态下，SVN提交后5分钟内更新统计；
- 支持400台开发客户端同时注册和周期性心跳；
- 支持160个仓库独立增量处理；
- 压力测试基线为每日5万条客户端归因事件；
- 普通查询的服务端P95响应时间目标不超过1秒；
- 领导总览使用预聚合数据，P95响应时间目标不超过2秒；
- 大文件、基线扫描和重算任务不得占用在线API线程。

## 16. 测试与验收

### 16.1 功能验收

- Windows和Linux客户端可在无公网环境安装、卸载和升级；
- Claude Code Edit、Write和Bash标准用例均产生正确归因；
- 标准测试语料中逐行AI归因结果100%一致；
- 人工修改、AI重写、删除、复制、重命名和分支复制后的存量正确；
- 有可靠mergeinfo的合并能够继承来源，歧义合并进入未归因；
- 部分文件提交只消费实际入库的AI行；
- 客户端和SVN事件乱序到达后能够得到相同最终结果；
- 重复事件不重复计数；
- 基线代码全部标记为历史未归因，不标记为人工代码；
- 指标能够下钻到仓库、版本号和归因事件。

### 16.2 故障验收

- 客户端断网24小时后恢复，积压数据完整补传；
- Linux后台停止时，VisualSVN提交正常完成；
- Hook Agent停止后恢复，缺失版本自动补采；
- 同一版本重复采集不会重复统计；
- 服务端处理中断后能够从持久任务恢复；
- 客户端缺失或版本断档时，页面显示数据质量告警并禁止作为考核数据。

### 16.3 安全验收

- 抓取客户端和Hook Agent请求，确认不包含提示词、回答正文和完整源代码；
- 无效、过期或已吊销凭据不能提交数据；
- 非授权角色不能查看人员级、项目级或路径级数据；
- 导出、配置和重算操作均生成审计记录；
- 安装包校验失败时安装程序拒绝继续。

### 16.4 性能验收

- 按400名开发人员、160个仓库、每日5万条归因事件执行压力测试；
- VisualSVN Hook在统计后台不可用时仍满足快速本地入队并正常返回；
- 正常负载下统计更新、查询和总览响应达到第15节目标；
- 基线扫描和重算期间SVN正常提交不受明显影响。

## 17. 实施边界与顺序

实施按可独立验收的能力拆分：

1. Rust公共协议、代码指纹和逐行来源算法；
2. Claude Code客户端采集、SQLite缓存和离线上报；
3. VisualSVN Hook入队、Windows服务、svnlook采集和版本补偿；
4. Linux接收服务、PostgreSQL任务、归因匹配和当前存量；
5. 统计指标、权限、管理页面、导出和审计；
6. Windows/Linux离线安装包、升级、部署和全链路验收。

每一阶段必须以自动化测试和可重复的离线部署验证作为完成条件。系统先在仿真仓库完成全部验收，再分批接入正式仓库；分批接入仅用于降低变更和性能风险，不改变系统面向全量400人、160个仓库建设的目标。
